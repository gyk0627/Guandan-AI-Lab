## 二、逐项核对（对照实测）

### GPU：RTX 4090 24GB —— ✅ 合理

- **显存**：我们的训练本身只占 **0.34 GB**（E17 补充）。24GB 对当前模型是**大量冗余**，
  但冗余有用：多进程自我对弈时，每个进程各占约 0.5 GB 上下文，
  24GB 可以支撑 **20~30 个并行推理进程**。
- **算力**：E19 显示当前训练步只用到峰值算力的 **1.55%**，
  瓶颈是 kernel launch 等固定开销。**4090 的高主频对"小算子多"的场景恰好有利**，
  但别指望它带来数倍提升——先用免费的 batch 放大和 CUDA Graphs。
- 一句话：**4090 合适，但收益要在软件优化之后才兑现。**

### CPU：EPYC 9354P（32C）vs 9654（96C）—— ⚠️ 这是唯一没数据的环节

- 本机实测（18 逻辑核）：自我对弈 **4~8 进程见顶 2.0–2.3×**，
  再加进程反而下降（E16）。但这是**笔记本的功耗/散热墙**，不能外推到服务器。
- 服务器上真正未知的是：**32 或 96 个进程同时向同一张 GPU 发推理请求时，GPU 会不会先饱和**
  （每个进程都是 batch=1 的小请求；单进程实测 1,900–2,900 次/秒）。
- **建议**：先买/租 **32C** 起步。若实测显示"CPU 还没吃满、GPU 已饱和"，96C 就是浪费；
  反之若 GPU 有余量、CPU 先满，再上 96C。
- 判断方法现成：到货第一天跑 `tools/scaling_test.py`（把档位加到 16/32/64），
  看吞吐在哪一档拐平。

### 内存：128GB —— ✅ 合理（但取决于核数）

- 每个自我对弈进程（torch + 模型）约 **0.8–1.5 GB**。
- 32C → 若开 32 进程 ≈ 30–50 GB；128GB 富余。
- 96C → 若开 96 进程 ≈ 80–150 GB；**128GB 会吃紧，需 256GB**。
- 所以内存与 CPU 核数要一起定，不能分开拍。

### 数据盘：2–4TB —— ✅ 取决于目标规模

实测单位（E02/E12）：
- 一局 ≈ **107 条决策**；JSONL ≈ **420 B/样本**，npz ≈ **184 B/样本**。

| 目标规模 | JSONL | npz | 合计 |
|---|---:|---:|---:|
| 100 万局 | ~45 GB | ~20 GB | ~65 GB |
| 1000 万局 | ~450 GB | ~200 GB | ~650 GB |
| 3000 万局 | ~1.3 TB | ~0.6 TB | ~1.9 TB |

- **2TB 够 1000 万局；4TB 才够 3000 万局。** 建议直接 4TB，NVMe 写速对导出也重要。
- 另需预留：模型 checkpoint、评估产物、测试临时文件（很小）。

### 系统盘 1TB / Ubuntu 24.04 —— ✅ 没问题

注意：Ubuntu 上需要重新验证 `tools/_sampler.ps1`（那是 Windows PowerShell 专用），
届时应换成 `nvidia-smi` + `/proc` 采样的 Linux 版本，否则基准工具无法跨平台对比。

## 三、下单前应做的"免费优化"（都不花钱，但直接影响配置收益）

按收益排序（全部有实测依据）：

1. **训练 batch 从 64 提到 512**：实测样本吞吐 **8.3 倍**（30,216 → 251,780/秒），
   且步时几乎不变（E19）。**配置买回来之前就该先做这个**，否则是在用新卡跑同样的瓶颈。
2. **CUDA Graphs**：把一步计算图固化，直接砍掉 launch 开销（E19 指出的主瓶颈）。
3. **导出并行化**：当前导出 440 样本/秒、单线程；按对局区间切分可接近 4 倍（E01/E17 推算）。
4. **训练数据预取**：`collate` 放后台线程，实测 **+10%**（E18）。
5. **多进程自我对弈的 GPU 争用测试**：在租来的机器上先跑，确定核数/GU 配比。

## 四、到货（或租到）第一天的验收流程

```bash
# 1. 机器性能基准（约 2 分钟）
python -m tools.benchmark_suite            # 记录 JSON，与 evaluation/benchmark_v1_baseline.json 对比

# 2. CPU 扩展性（关键：决定该开多少进程/该买多少核）
python -m tools.scaling_test --configs 1,2,4,8,16,32 --games 60

# 3. 训练扩展性（batch 扫描，确认 launch 开销是否随卡变好）
python -m tools.roofline_probe

# 4. 数据管线吞吐（生成 → 导出 的实际配比）
python -m tools.speed_test --games 500
```

验收判据：
- 若 scaling 在 32 进程处仍在上升 → **CPU 不够，值得上 96C**；
- 若在 16~24 进程处拐平且 GPU 占用接近满 → **32C 足够，钱花在 GPU 上**；
- 若 training epoch 时间没比笔记本快多少 → **先做 batch/CUDA Graphs，再谈换卡**。

## 五、对这份配置的最终意见

| 项 | 意见 |
|---|---|
| 方向（均衡型、不堆显存） | ✅ 正确，与 E19 结论一致 |
| RTX 4090 24GB | ✅ 合适；显存冗余对多进程推理有用 |
| EPYC 32C vs 96C | ⚠️ **先 32C**，用实测决定是否加核（唯一无数据项） |
| 内存 128GB | ✅ 配 32C 合理；若上 96C 要 256GB |
| 数据盘 | ✅ 建议直接 4TB（支持 3000 万局），2TB 只够 1000 万局 |
| 系统 Ubuntu 24.04 | ✅ 但需重写资源采样器（Windows 专用脚本不可用） |
| **最大的风险** | **高核数下"CPU 引擎 ↔ 单卡推理"的配比未知**，务必先租机实测 |

> 换句话说：**这份配置可以买，但请先在云上租一台同规格机器跑一遍上面的四条命令。**
> 一天租金远小于买错 64 核的代价。
