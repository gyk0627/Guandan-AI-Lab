## E01 · 吞吐量基准（2026-11-03）

**目的**：估算大规模自我对弈的成本，决定租服务器的配置（CPU 核数 vs GPU）。

**命令**

```powershell
& .\.venv\Scripts\python.exe -X utf8 -m tools.benchmark_throughput --games 10 --selfplay-games 3
```

**结果**

| 环节 | 吞吐 |
|---|---|
| CPU · 随机对局（单核） | 10.0 局/秒 · 1232 决策/秒（102 ms/局） |
| CPU · 启发式对局（单核） | 5.2 局/秒 · 511 决策/秒（186 ms/局） |
| GPU · 候选打分 batch=1 | 2,628 决策/秒（0.4 ms/批） |
| GPU · 候选打分 batch=64 | 156,937 决策/秒（0.4 ms/批） |
| 端到端自我对弈（引擎+模型） | 2.88 局/秒（325 ms/局） |

**规模估算（单核）**

| 策略 | 100 万局 | 1000 万局 | 1000 万局数据量 |
|---|---:|---:|---:|
| 随机 | 27.8 h | 278 h | ~700 GB |
| 启发式 | 53.1 h | 531 h | ~700 GB |
| 端到端（模型） | 96.4 h | 964 h | ~700 GB |

**结论（对论文很重要）**：**瓶颈在 CPU 规则引擎，不在 GPU**。GPU 每秒能处理 15.7 万个决策，
而引擎单核每秒只产出 511~1232 个决策。因此扩容应优先加 CPU 核数（近线性扩展），
GPU 在 32 核以内都不会成为瓶颈。

## E05 · 一步前瞻策略：**负结果**（2026-11-03）

**目的**：用 E04 的价值网络，在行为克隆的 top-K 候选之间做裁决，检验能否超过纯行为克隆。

**设计**
1. 行为克隆（BC）给全部候选打分，取 top-K；
2. 对每个候选在引擎里真实模拟执行（`copy.deepcopy` 局面）；
3. 价值网络评估模拟后的局面（从下一个行动者视角，换算成我方头游概率）；
4. 取我方概率最高的动作。

候选数 > 60 时退回 BC（编码 500 个候选本身就需 200 ms，见 E01）。
所有评估均用 `tools/eval_policies.py`：**同一评估器、同一批种子（300..399）、每组换边两局**。

**命令**

```powershell
& .\.venv\Scripts\python.exe -X utf8 -m tools.eval_policies --a neural    --b heuristic --games 100 --seed-start 300
& .\.venv\Scripts\python.exe -X utf8 -m tools.eval_policies --a lookahead --b heuristic --games 100 --seed-start 300 --top-k 1
& .\.venv\Scripts\python.exe -X utf8 -m tools.eval_policies --a lookahead --b heuristic --games 100 --seed-start 300 --top-k 3
& .\.venv\Scripts\python.exe -X utf8 -m tools.eval_policies --a lookahead --b heuristic --games 100 --seed-start 300 --top-k 5
& .\.venv\Scripts\python.exe -X utf8 -m tools.eval_policies --a lookahead --b heuristic --games 100 --seed-start 300 --top-k 5 --min-value-gap 0.15
```

**结果（每组 200 局，配对设计）**

| 策略 | 胜场 / 总局数 | 胜率 | 95% CI | 前瞻触发率 |
|---|---|---:|---|---:|
| **纯行为克隆（基线）** | 103 / 200 | **51.50%** | 44.61–58.33% | — |
| 前瞻 top_k=1（**对照组**） | 103 / 200 | **51.50%** | 44.61–58.33% | 86.7% |
| 前瞻 top_k=3 | 69 / 200 | 34.50% | 28.26–41.32% | 89.5% |
| 前瞻 top_k=5 | 52 / 200 | 26.00% | 20.41–32.49% | 87.9% |
| 前瞻 top_k=5 + 价值差门槛 0.15 | 84 / 200 | 42.00% | 35.37–48.93% | 87.9% |
| 前瞻 top_k=5 **vs 行为克隆**（直接对打） | 49 / 200 | **24.50%** | 19.06–30.90% | 90.8% |
| 前瞻 top_k=5，换成**最好的价值网络**（E10，AUC 0.6426） | 63 / 200 | **31.50%** | 25.46–38.24% | 90.4% |

**关键对照**：`top_k=1` 时不应发生任何覆盖，结果与基线**逐局完全相同**（103/200，
且同一批种子下连胜负分布都一致）。这说明**前瞻管线本身没有 bug**，
"前瞻更差"是价值判断错误导致的，不是实现错误。

**结论（负结果，但结论很硬）**

1. **让价值网络裁决得越多，棋力越差**，且单调（1 → 3 → 5：51.5% → 34.5% → 26.0%）；
2. 加保守门槛（只有价值差 > 0.15 才覆盖）能挽回一部分（42.0%），但仍不如基线；
3. 因此瓶颈**不是搜索过程，而是价值网络**：
   * E04 的验证 AUC 只有 0.635，且从第 4 轮起过拟合；
   * 一步前瞻的价值差通常只有 0.01~0.05，**低于价值网络自身的误差**，
     于是"裁决"实际上是往一个还不错的策略里注入噪声；
4. 与文献一致：**价值评估的质量决定前瞻搜索的价值**。

**对论文的意义**：这一节说明"简单地加一步前瞻并不自动变强"，
并给出了可复现的证据链（对照组精确复现基线）。下一步必须提高价值估计质量，
而不是继续加搜索深度。

## E07 · 价值网络的数据量缩放曲线（2026-11-03）

**目的**：分离"数据量"与"数据分布"两个变量。从同一份 5000 局数据里按固定种子
抽样出不同局数，各训一个价值网络，唯一变量是局数。

**命令**

```powershell
& .\.venv\Scripts\python.exe -X utf8 -m tools.value_scaling --sizes 300,1000,2000,5000 --epochs 20
```

**结果**

| 训练局数 | 样本数 | 最佳轮次 | 验证 AUC |
|---:|---:|---:|---:|
| 300 | 28,789 | 3 | 0.5491 |
| 1,000 | 95,748 | 20 | 0.5234 |
| 2,000 | 191,608 | 16 | 0.6197 |
| 5,000 | 478,895 | 3 | **0.6351** |

（产物：`evaluation/value_scaling.json`）

**结论**

1. 价值 AUC **随数据量上升**（0.55 → 0.62 → 0.635），5000 局处仍未饱和；
2. 1000 局那个点是噪声（20 轮仍在训练、过拟合极快），不作为趋势点；

**推论（对研究路线的影响）**：要让一步前瞻真正有效，价值网络需要比现在多 1~2 个数量级的
自我对弈数据。而 E01 的吞吐基准显示这在本机不现实（1000 万局 ≈ 964 核时），
需要多核服务器并行模拟——**这也解释了为什么下一步是"扩算力"而不是"加算法"**。

## E08 · 并行自我对弈（2026-11-03）

**目的**：E01 说明瓶颈在 CPU 引擎，那就用多进程直接扩。测实际加速比。

**实现**：按种子区间切分，每个进程独立跑一段、写自己的分片文件，父进程合并。
**没有用 `multiprocessing.Pool`**：Windows 上 Pool 依赖命名管道，受限环境会拒绝创建；
改用 `subprocess` + `DEVNULL` 完全不走管道。

**命令**

```powershell
& .\.venv\Scripts\python.exe -X utf8 -m training.self_play --games 200 --workers 1 --seats neural,neural,neural,neural --temperature 0 --epsilon 0 --seed-start 300000 --out tmp\par_w1.jsonl
& .\.venv\Scripts\python.exe -X utf8 -m training.self_play --games 200 --workers 4 --seats neural,neural,neural,neural --temperature 0 --epsilon 0 --seed-start 300000 --out tmp\par_w4.jsonl
```

**结果**

| 进程数 | 局数 | 墙钟 | 吞吐 | 加速比 |
|---:|---:|---:|---:|---:|
| 1 | 200 | 66.3 s | 3.02 局/秒 | 1.00× |
| 4 | 200 | 21.8 s | 9.17 局/秒 | **3.04×（效率 76%）** |

4 进程拿不到 4 倍：四个进程共享同一块 GPU 做推理，存在排队。

**对服务器预算的推算**：按 3.0 局/秒/4 进程 = 约 0.75 局/秒/核，
1000 万局 ≈ 3700 核时。32 核服务器约 **115 小时**（约 5 天），64 核约 58 小时。
若能接受 100 万局，则 32 核约 11.5 小时。

**产物**：`training/data_selfplay/` 下的分片合并文件与 manifest（含吞吐字段）。

## E09 · 价值网络正则化扫描：**负结果**（2026-11-03）

**假设**：E04 过拟合严重（训练 AUC 0.97 / 验证 0.63），加正则应该能提高验证 AUC。

**命令**

```powershell
& .\.venv\Scripts\python.exe -X utf8 -m training.train_value --epochs 20 --weight-decay 0.01 --out models\value_wd.pt
& .\.venv\Scripts\python.exe -X utf8 -m training.train_value --epochs 20 --dropout 0.3 --weight-decay 0.01 --hidden 128 --out models\value_drop.pt
& .\.venv\Scripts\python.exe -X utf8 -m training.train_value --epochs 20 --dropout 0.5 --weight-decay 0.05 --hidden 64 --out models\value_small.pt
```

**结果**

| 配置 | 最佳轮次 | 验证 AUC |
|---|---:|---:|
| 基线（hidden 256，无正则） | 3 | **0.6351** |
| weight_decay 1e-2 | 16 | 0.5347 |
| dropout 0.3 + wd 1e-2 + hidden 128 | 1 | 0.5357 |
| dropout 0.5 + wd 5e-2 + hidden 64 | 1 | 0.5000（模型塌缩成常数输出） |

**结论（负结果）**：加正则**反而更差**。原因是峰值 AUC 出现在**第 3 轮**，
正则化压低了早期拟合速度，20 轮内没能回到原来的峰值；
而"过拟合"发生在峰值之后，对"取最佳验证轮"的流程无害。
**最稳的做法是早停 + 不加正则**，而不是加大正则。

## E10 · 合并数据集训练价值网络（2026-11-03）

**目的**：E06（只用 1000 局克隆数据）AUC 0.556、E07（数据量曲线）显示数据越多越好。
合并"5000 局老师数据 + 1000 局克隆数据"（共 6000 局），看策略混合是否有额外收益。

**命令**

```powershell
& .\.venv\Scripts\python.exe -X utf8 -m training.merge_datasets training\data\games_20261103_121919.npz training\data_selfplay\bc_policy_1000.npz --out training\data_selfplay\merged_6000.npz
& .\.venv\Scripts\python.exe -X utf8 -m training.train_value --data training\data_selfplay\merged_6000.npz --epochs 20 --out models\value_merged_6000.pt
```

**结果**

| 数据集 | 局数 | 样本 | 最佳轮次 | 验证 AUC |
|---|---:|---:|---:|---:|
| 仅老师数据（E04） | 5,000 | 478,895 | 3 | 0.6351 |
| 老师 + 克隆混合（E10） | 6,000 | 580,805 | 5 | **0.6426** |

**结论**：混合数据把 AUC 从 0.635 提到 **0.643**（+0.008），方向正确但幅度很小。
配合 E07 的缩放曲线（300→5000 局只从 0.55 涨到 0.635），可以判断：
**价值 AUC 对数据量的边际收益很低**，靠"堆数据"把 AUC 推到 0.8 以上并不现实。
这提示真正的改进方向是**状态表示**（现在 198 维只含点数、张数、部分历史，缺少出牌序列与手牌结构信息），
而不是单纯加数据量。

**补充验证**：用这个 AUC 更高（0.6426）的价值网络重跑 E05 的一步前瞻，
胜率 **31.50%**（63/200，CI 25.46–38.24）——仍远低于 BC 的 51.50%。
说明"换一个稍好的价值网络"救不了前瞻，差的不是那 0.008 的 AUC。

## E11 · 状态表示 v3：把出牌历史编码进去（2026-11-03）

**动机**：E07/E10 说明价值网络的瓶颈不是数据量，而是**状态表示**——
v2 的 198 维只有"上一手"，网络看不到之前发生了什么（谁在控场、谁在过牌、双方节奏）。

**改动**（`training/state_encoder.py`，198 → 258 维）：

| 新增段 | 维度 | 内容 |
|---|---:|---|
| `history_seats` | 24 | 最近 6 手的出牌者相对座位（4×6） |
| `history_features` | 24 | 每手：是否过牌 / 牌型 / 张数 / 主牌力（4×6） |
| `team_progress` | 2 | 双方各自已出多少张（/54） |
| `team_finished` | 2 | 双方各出完几人（/2） |
| `bombs_played` | 2 | 双方已用炸弹数（/4） |
| `hand_structure` | 6 | 王数、逢人配数、成对点数、成三点数、炸弹组数、最大炸弹张数 |

同时加了**编码器版本校验**：checkpoint 记录 `encoder_version`，
用 v2 模型配 v3 编码器会在加载时报可读错误（实测报错信息见下方），
而不是形状不匹配的堆栈。

**命令**

```powershell
& .\.venv\Scripts\python.exe -X utf8 -m training.export_dataset training\data\games_20261103_121919.jsonl --out training\data\games_20261103_v3.npz
& .\.venv\Scripts\python.exe -X utf8 -m training.train_bc --data training\data\games_20261103_v3.npz --epochs 40 --batch-size 64 --min-candidates 2
& .\.venv\Scripts\python.exe -X utf8 -m tools.eval_policies --a neural --b heuristic --games 100 --seed-start 300
```

**结果**

| 指标 | v2（198 维） | v3（258 维） | 变化 |
|---|---:|---:|---|
| 行为克隆验证一致率 | 0.7562 | 0.7500 | -0.006 |
| 最难桶（候选 101+）一致率 | 0.429 | 0.385 | -0.044 |
| 行为克隆对启发式胜率（200 局配对） | 51.50% | **53.00%** | +1.5pt（CI 46.09–59.80，与 51.5% 重叠） |
| **价值网络验证 AUC** | 0.6351 | **0.6997** | **+0.065** |

**关键发现**

1. **动作一致率没提升甚至略降**。这符合预期：标签是**启发式老师**的动作，
   而老师的决策几乎不依赖历史——多给历史特征并不能更好地模仿老师。
   所以"加特征 → 一致率变高"这个假设本身就不成立。
2. **价值 AUC 明显提升（0.635 → 0.700）**。价值预测恰恰需要历史：
   谁在控场、谁在过牌、双方节奏，都是判断胜负的关键。
   这是目前所有实验里单项最大的一次提升。
3. 行为克隆胜率 51.50% → 53.00%，方向为正但差异在噪声内。

**随后用 AUC 0.70 的价值网络重跑一步前瞻（关键对照）**

| 前瞻配置 | 价值 AUC | 对启发式胜率 |
|---|---:|---:|
| top5 + v2 价值网络 | 0.635 | 26.00% |
| **top5 + v3 价值网络** | **0.700** | **16.50%**（CI 12.00–22.27） |
| top3 + 价值差门槛 0.1 + v3 价值网络 | 0.700 | 39.50%（CI 32.98–46.41） |
| 纯行为克隆（v3） | — | **53.00%** |

**结论（本文最有价值的分析点）**：

> **全局 AUC 提升，前瞻反而更差。**

- 价值网络更"准"了，但它评估的是**跨对局的全局排序**；
  而前瞻需要的是**同一局面下兄弟动作之间的相对偏好**。两者不是一回事。
- 更进一步的假设：价值网络在**老师分布**上训练，前瞻会把它推到分布外；
  网络越拟合训练分布，在分布外的自信错误就越致命（AUC 0.635 时错得"软"，
  AUC 0.700 时错得"硬"）。
- 因此：**"训练一个更准的价值网络"不等于"让搜索变得有用"**；
  论文应把这一点作为方法学结论，并指出需要**决策内偏好指标**（例如
  "老师动作 vs 其它动作"的价值排序准确率），而不是全局 AUC。

## E13 · 决策内偏好测试：价值网络能不能在同一个局面里分出好坏（2026-11-03）

**动机**：E11 发现"全局 AUC 提高（0.635→0.700），一步前瞻反而更差（26%→16.5%）"。
一个直接解释是：**AUC 衡量跨对局排序，前瞻需要同一局面下兄弟动作的排序**。
本实验直接测后者。

**做法**（不需要训练，全部现算；工具 `tools/decision_preference.py`）：

1. 用启发式策略重放 N 局，沿它的轨迹走；
2. 每个采样决策点：候选 = 合法出牌 + 过牌；"正确答案" = 启发式此刻的选择；
   随机抽 K 个其它候选作陪衬；
3. 对每个动作**真实模拟执行**，用价值网络评估"走完这步后我方头游概率"；
4. 统计老师动作排第一的比例，与随机基线 1/(K+1) 比。

**对照**：同一批决策上，用**策略网络**做同样的排序（它应该明显高于随机，
用来证明测试工具本身没坏）。

**命令**

```powershell
& .\.venv\Scripts\python.exe -X utf8 -m tools.decision_preference --games 40 --alternatives 4 --value-checkpoint models\value_v3.pt --policy-checkpoint models\bc_games_20261103_v3.pt
& .\.venv\Scripts\python.exe -X utf8 -m tools.decision_preference --games 40 --alternatives 1 --value-checkpoint models\value_v3.pt
```

**结果（1590 次采样决策，40 局）**

| 谁在排序 | 老师动作排第一 | 95% CI | 随机基线 |
|---|---:|---|---:|
| **价值网络（AUC 0.700）**，K=4 | **28.81%**（458/1590） | 26.63–31.08% | 20% |
| 价值网络，K=1（二选一） | 55.14%（869/1576） | 52.67–57.58% | 50% |
| **对照：策略网络**，K=4 | **59.06%**（939/1590） | — | 20% |

**结论（本文核心证据）**

1. **工具可信**：策略网络在同一批决策上能到 59.06%（远高于随机 20%），
   说明测试流程没有坏，价值网络的低分是真实的能力问题。
2. **价值网络几乎没有决策内分辨力**：K=4 时 28.81%（比随机高 8.8 个百分点），
   K=1 时 55.14%（只比抛硬币高 5.1 个百分点）。
3. 这直接解释了 E05/E11：一步前瞻要在兄弟动作间做裁决，
   而价值网络在这个维度上**只比瞎猜稍好**——所以它越"自信"地裁决，伤害越大。
4. **因此"全局 AUC"不能作为价值网络可用于搜索的判据**；
   论文应改用**决策内偏好准确率**作为核心指标。

**复现注意**：该工具要求价值网络的 `state_dim` 与当前编码器一致
（v2 的 198 维权重在 v3 编码器下会给出可读报错）。

## E14 · 成对比较训练（RLHF 奖励模型的先导版）：**负结果**（2026-11-03）

**动机**：E13 显示价值网络在决策内几乎没有分辨力（28.81%）。
既然"回归绝对值"学不好，就改成"学比较"——这正是 RLHF 里奖励模型的做法，
只是用启发式老师代替人类偏好。

**做法**（`training/train_pairwise.py`）

- 每个样本构造一对：老师动作（正）+ 一个陪衬（负）；
- **难负样本优先**：同牌型 + 同张数但不是老师那张（比例 0.75），逼模型学细微差别；
- 模型结构与行为克隆完全相同（`CandidateScorer`），只换损失：
  成对逻辑损失 `BCE(sigmoid(score_pos − score_neg))`。

**命令**

```powershell
& .\.venv\Scripts\python.exe -X utf8 -m training.train_pairwise --epochs 30 --out models\pairwise_v3.pt
& .\.venv\Scripts\python.exe -X utf8 -m tools.eval_policies --a neural --b heuristic --games 100 --seed-start 300 --checkpoint models\pairwise_v3.pt
& .\.venv\Scripts\python.exe -X utf8 -m tools.eval_policies --a neural --b neural --games 100 --seed-start 300 --checkpoint models\pairwise_v3.pt --b-checkpoint models\bc_games_20261103_v3.pt
```

**结果**

| 指标 | 行为克隆 | 成对比较 |
|---|---:|---:|
| 决策内排第一（同一评估函数，48,048 条验证集） | **0.8200** | 0.7462 |
| 成对训练准确率（训练集） | — | 0.904 |
| **对启发式（200 局配对）** | **53.00%** | **29.00%**（CI 23.15–35.64） |
| **对行为克隆（200 局配对）** | — | **20.50%**（CI 15.49–26.63） |

**结论（负结果，但对 RLHF 路线很重要）**

1. **单负样本的成对目标学不到全局排序**：它只约束"这一对谁更高"，
   没有 softmax 那样的跨候选归一化，所以"分数最高的候选"并不可靠——
   模仿率（74.6% vs 82.0%）和实战（29% vs 53%）双双落后。
2. 这说明**奖励模型的用法不能是"直接对候选取 argmax"**。
   在 RLHF 里，奖励模型是给**策略优化**（PPO + KL 约束）提供信号的，
   不是替代策略网络做动作选择。
3. 对论文的意义：这条负结果直接支撑 §8 的设计——
   **RLHF 校准必须是"偏好信号 + 策略优化"，而不是"换个损失函数重训一遍"**。

**方法论提醒（踩过的坑）**：本实验第一次评估出 0.18 的荒谬数字，
原因是评估函数把"验证集子集的 states"和"全量 cand_offsets"混用导致索引错位；
用行为克隆模型做同函数对照（应为 0.82）才发现是工具错，不是模型错。

## E15 · 软标签价值网络：只改标签形状不够（2026-11-03）

**动机**：Soft-DMC 的第一层含义是"软价值目标"。最便宜的软化方式：
把"赢/输"的硬标签换成 **0.5 × 胜负 + 0.5 × (升级数 / 3)**——
掼蛋里"赢 3 级"和"赢 1 级"的局势质量差别很大，硬标签把这些抹掉了。

**命令**

```powershell
& .\.venv\Scripts\python.exe -X utf8 -m training.train_value --data training\data\games_20261103_v3.npz --epochs 20 --target soft --out models\value_v3_soft.pt
& .\.venv\Scripts\python.exe -X utf8 -m tools.decision_preference --games 40 --alternatives 4 --value-checkpoint models\value_v3_soft.pt
```

**结果**

| 指标 | 硬标签（E04/E11） | 软标签（E15） |
|---|---:|---:|
| 验证 AUC（对硬胜负计算，保证可比） | 0.6997 | 0.6954 |
| **决策内偏好（K=4，随机 20%）** | 28.81% | **29.18%**（CI 27.00–31.46） |
| 老师动作的价值优势（均值） | +0.0190 | +0.0157 |

**结论（负结果）**：**只把标签软化，几乎没有效果**（+0.37 个百分点，噪声内）。

**为什么重要**：它把问题定位得更准了——
真正的缺口不是"标签的分布形状"，而是**训练信号里没有"同一局面下兄弟动作的比较"**。
价值网络学的是"这个局面好不好"，而不是"这两个相邻局面哪个更好"。

**下一步设计方向（E16 候选）**：**兄弟对监督（sibling supervision）**——
用引擎对同一决策点的不同候选各自模拟一步，构造"动作 A 之后的状态 vs 动作 B 之后的状态"，
直接训练价值网络**比较相邻状态**（而不是比较整局）。这才是"软"在决策层面的正确用法。

## E17 · GuanDan Benchmark：机器选型的第一版基准（2026-11-03）

**目的**：把"这台机器能跑多快"变成**可对比的标准报告**——换机器/租服务器时跑同一套，
用数据决定买什么，而不是拍脑袋。

**覆盖模块**（可选跑哪几个）

| 模块 | 测什么 |
|---|---|
| `cpu` | 纯 CPU 模拟吞吐（启发式，不碰 GPU）：局/秒、决策/秒 |
| `inference` | GPU 推理独立测试：batch 1/8/16/32/64/128 的 推理/秒、每批耗时；**另测 CPU 端数据准备** |
| `train` | 行为克隆与价值网络各跑 N 轮（真跑）：秒/轮、最佳指标 |
| `export` | 数据导出：样本/秒、局/秒 |
| `pipeline` | 端到端：生成对局 → 导出 → 训练 1 轮 |

每次运行还会采样整机资源：CPU%、GPU 利用率（均值/峰值）、显存峰值、功耗、温度。

**命令**

```powershell
& .\.venv\Scripts\python.exe -X utf8 -m tools.benchmark_suite
& .\.venv\Scripts\python.exe -X utf8 -m tools.benchmark_suite --modules cpu,inference
& .\.venv\Scripts\python.exe -X utf8 -m tools.benchmark_suite --compare evaluation\benchmark_v1_baseline.json
```

**v1 基准结果（本机：RTX 5060 Laptop / 18 逻辑核 / CUDA）**

| 项目 | 数值 |
|---|---|
| CPU 模拟 | 4.73 局/秒 · 458.8 决策/秒 |
| GPU 推理 batch=1 | 1,897 推理/秒（0.53 ms/批） |
| GPU 推理 batch=64 | 162,733 推理/秒（0.39 ms/批） |
| GPU 推理 batch=128 | 293,644 推理/秒（0.44 ms/批） |
| 数据准备 | 状态 0.038 ms + 每候选 0.006 ms |
| 训练 | BC 31.3 秒/轮；value 7.3 秒/轮（含数据加载与验证） |
| 数据导出 | 426.8 样本/秒 · 4.40 局/秒 |

1. **推理吞吐随 batch 近似线性**（batch 128 是 batch 1 的 155 倍），说明网络很小、

3. 显存峰值 4.3 GB 出现在 BC 训练（候选补边到批内最大宽度），**这是 8 GB 卡的上限约束**：
   租服务器时显存不是主要瓶颈，但这解释了为什么 16 进程同时训练会吃紧。

| **PyTorch 显存峰值** | **0.34 GB** | 这是训练本身真正占用的显存 |
| nvidia-smi 整机显存 | 4,336 MB | 包含浏览器/桌面等其它进程，**不是我们的训练** |
| 时间构成 | 数据准备 15% / GPU 计算 85% | 数据加载不是瓶颈 |
| CPU | 20.7%，**仅 1 / 18 核忙** | 训练循环是单线程的 |
| GPU 利用率（**任务管理器口径**） | **峰值 96% / p95 96% / 均值 78%** | 见下方更正：训练时 GPU 接近打满 |
| GPU 利用率（nvidia-smi 口径） | 峰值 45% / 均值 26% | 该指标在 Windows/WDDM 上**低估** |
| GPU 频率 / 功耗 / 温度 | 峰值 2,955 MHz / 均值 28.4 W / 53℃ | 远未触及功耗墙 |

> ⚠️ **更正（2026-11-04）**：本节最初写的是"GPU 峰值只有 39%，说明没打满、瓶颈在 Python"。
> 用**任务管理器同一个数据源**（Windows `GPU Engine` 性能计数器，按引擎类型统计）重测后，
> 训练期间 3D 引擎利用率是 **87%–97%**。`nvidia-smi utilization.gpu` 统计的是
> "有 kernel 在执行的时间占比"，对"大量小 kernel + Python 间隔"的场景会严重低估。
> **原结论撤回**：训练时 GPU 是接近饱和的，换更快的显卡确实能提升训练速度。
> 现已在 `tools/gpu_metrics.py` 中统一采集两种口径，两个测速器都会打印任务管理器口径。
>
> ⚠️ **进一步更正（E19 之后）**：那个"96% 忙"**不等于算力吃满**。Roofline 实测显示
> 训练步只用到峰值的 **1.55% 算力、0.40% 带宽**，且 batch 从 64 加到 512 步时几乎不变——
> 真正的瓶颈是**每步的固定开销（kernel launch / 小算子调度）**。
> 因此"换更强的 GPU"在当前模型规模下收益有限，**应先加大 batch 或上 CUDA Graphs**。
> 详见 E19。

**结论（对硬件选型）**

1. **本次训练真正只需要约 0.35 GB 显存**。24 GB 显存对这个模型是**极大冗余**；
   8 GB 的笔记本卡已经够用。
2. 但**显存会不会成为瓶颈，取决于模型与批量**：如果以后把网络放大、batch 提大、
   或多进程同时训练，显存占用会线性上升——那时 24 GB 才有意义。
3. 训练阶段 **GPU 引擎利用率 87%–97%（任务管理器口径）**、CPU 只有 1 个核在忙：
   说明 **GPU 是训练阶段的瓶颈**（数据准备只占 15%，E18 也验证了这一点）。
   因此"换更快显卡对训练无用"的说法**不成立**；有效方向是更快的 GPU、更大的 batch，
   以及把 collate 放进后台线程（E18 实测 +10%）。

**给下一台工作站的直接建议**（结合 E19 修正）：

1. **显存**：当前模型训练只占 0.34 GB，**24 GB 足够，不必上 48 GB**；
   只有把模型放大 5~10 倍（更多层/更大 hidden）才需要 32 GB 以上。
2. **单卡算力**：先别急着为训练加钱——E19 显示训练步只用到峰值算力的 1.55%，
   且加大 batch 几乎不增加步时。**先做两件不花钱的事**：把 batch 提到 512、上 CUDA Graphs。
   做完再测，如果那时算力占比上来了，换卡才有意义。
3. **CPU 核**：**自我对弈才是 CPU 大户**（E16：本机 4~8 进程见顶 2.0–2.3×，
   服务器上应实测后再定核数）。工作站预算优先给 CPU 核与内存带宽。

## E18 · 数据准备是不是训练瓶颈（等价于 DataLoader num_workers）（2026-11-03）

**背景**：有建议测试 DataLoader 的 `num_workers = 0/1/2/4/8`。
但**本项目没有用 `DataLoader`**——组批是 `training.dataset.collate`（numpy 补边）在主进程里做的，
所以没有 `num_workers` 这个参数。本实验做**等价对比**：把组批放到后台线程预取，
让 CPU 在 GPU 计算时准备下一批。

**命令**

```powershell
& .\.venv\Scripts\python.exe -X utf8 -m tools.dataloading_test --prefetch 0,1,2,4 --seconds 4
```

**结果（v3 数据，batch=64，每种配置跑 4 秒）**

| 预取线程 | 步/秒 | ms/步 | 样本/秒 | 等待数据 ms | 计算 ms |
|---:|---:|---:|---:|---:|---:|
| 0（同步） | 279.0 | 3.59 | 17,844 | 0.25 | 3.33 |
| 1 | 300.8 | 3.33 | 19,240 | 0.14 | 3.14 |
| **2** | **306.5** | **3.26** | **19,613（+9.9%）** | 0.14 | 3.08 |
| 4 | 302.3 | 3.31 | 19,343（+8.3%） | 0.13 | 3.13 |

**结论**

1. **数据准备确实是次要瓶颈**：双线程预取能带来约 **+10%** 吞吐；
   再加线程没有更多收益（4 线程反而略降，线程调度开销）。
2. 但**不是主要瓶颈**：等待数据只占每步 0.25 ms / 3.59 ms ≈ **7%**，
   与 E17 补充里"数据 15% / 计算 85%"的结论一致。
3. 与 E16 呼应：**给训练加 CPU 核没有意义**（上限 +10%），
   CPU 核应该花在**自我对弈**上（那里才是 CPU 引擎主导），而不是训练。

**可直接采用的优化**：把 `collate` 放进后台线程预取（2 个线程），
训练吞吐约 +10%，代价很小——已记录为可选实现，尚未接入 `train_bc` 默认流程。

## E19 · Roofline 分析：训练时 GPU 是算力受限还是带宽受限（2026-11-04）

**问题**：任务管理器显示训练时 GPU 3D 引擎 92%–97%，那到底是**计算单元吃满**，
还是**显存带宽限制**？

**方法**（`tools/roofline_probe.py`）

1. 实测本机上限：大矩阵乘 TFLOPS、大块拷贝 GB/s，算出脊点（FLOP/Byte）；
2. 用 `torch.utils.flop_counter` 精确数一次训练步（前向+反向）的 FLOPs；
3. 估算该步要搬的字节（输入 + 参数×3），求算术强度；
4. 用**固定宽度**的合成张量只变 batch，看步时是否随工作量增长。

**命令**

```powershell
& .\.venv\Scripts\python.exe -X utf8 -m tools.roofline_probe
```

**结果**

[1] 本机上限（实测）

| 项 | 值 |
|---|---:|
| 矩阵乘算力 | 9.49 TFLOPS |
| 显存带宽 | 284.6 GB/s |
| 脊点 | 33.3 FLOP/Byte |

[2] 我们的训练步（batch=64）

| 项 | 值 |
|---|---:|
| FLOPs/步 | 0.29 GFLOP |
| 字节/步（上界估计） | 2.26 MB |
| 步时 | 1.93 ms |
| **实际算力** | **0.148 TFLOPS（峰值的 1.55%）** |
| **实际带宽需求** | **1.17 GB/s（峰值的 0.40%）** |
| 算术强度 | 126.5 FLOP/Byte（**高于**脊点 33.3） |

[3] batch 放大（固定候选宽度 30，只变 batch）

| batch | ms/步 | 样本/秒 |
|---:|---:|---:|
| 64 | 2.12 | 30,216 |
| 128 | 2.07 | 61,771 |
| 256 | 2.08 | 123,221 |
| 512 | **2.03** | **251,780** |
| 1024 | 2.92 | 351,018 |

**结论（本文对 GPU 瓶颈的最终判断）**

1. **既不是算力受限，也不是带宽受限**：算力只用到峰值的 1.55%、带宽只用到 0.40%，
   两者都远远没到顶。
2. 关键证据是 [3]：**batch 从 64 加到 512，工作量涨 8 倍、步时几乎不变（2.12 → 2.03 ms）**。
   这说明一步的时间主要花在**固定开销**上——kernel launch、小算子调度、Python↔CUDA 交互；
   算力和带宽都还没轮到成为瓶颈。
3. 所以任务管理器里那个 96% 的含义是：**引擎在不停处理"很小的活"**，并不等于
   "计算单元在做很多数学运算"。这解释了"引擎很忙但吞吐很低"的表面矛盾。

**可操作的结论（按收益排序）**

1. **先把每步做多一点**：batch 512 相比 64，样本吞吐约 **8.3 倍**（同一步时）。
   训练脚本默认 batch=64，这里有很大的空间（需验证收敛影响）。
2. **消除 launch 开销**：用 CUDA Graphs 把一步的计算图固化，能直接砍掉这部分固定成本。
3. **换更强的 GPU 收益有限**：在"每步只算 0.29 GFLOP"的规模下，换卡主要改善的是
   固定开销而非算力——**先把 batch/模型放大，再谈换卡**。
4. 与 E16/E17 一致：**多进程自我对弈才是该买 CPU 核的地方**（那里 CPU 引擎是瓶颈）。
