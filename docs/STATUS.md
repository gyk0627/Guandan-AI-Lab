## 四、已知缺陷与限制（按影响排序）

### 4.1 【已修复】评估器 `pairs` 键冲突

- 现象（修复前）：`python main.py evaluate --json` 输出的 `pairs` 不是组数，而是字典
  `{"total": 1, "sweep_win": 1, ...}`；表格里打印成「总对局数：200（{'total': 100, ...} 组 × 2 局）」。
- 原因：`run_head_to_head` 里 `summary = dict(config); summary.update(stats)`，
  `config["pairs"]`（整数）与 `stats["pairs"]`（字典）同名，后者覆盖前者。
- 现状：**已修复**——`stats` 的键改名为 `pair_outcomes`，`summary["pairs"]` 保持为组数；
  `tests/test_cli.py::test_evaluate_json_summary` 已绿。
- 保留此条的原因：它是一个**典型教训**——新增统计字段时先看有没有同名字段。
  修法与验证过程写在这里，供后续同类问题参考。

### 4.2 【规则争议】「不能压队友」被硬编码

- `game_state.py::get_legal_moves` 在「上一手是队友」时返回**空列表**。
- 结果：这名玩家在引擎层面**没有合法牌**，只能过牌；策略无法表达「我就是要压队友」。
- 确认表没有这一条（见 RULES.md Q1）。在负责人回答前，**不要改动行为，也不要把它写成规则文档里的既定事实**。

### 4.3 【已修复】`check_dataset.py` 曾与 v2 采集器不兼容

- 修复前：它找 `training_data_*.jsonl`、校验 `sample["state"]` 与 `sample["candidate_actions"]`（v1 格式），
  而 v2 采集器写的是 `training/data/games_*.jsonl`，**没有** `state` / `candidate_actions` → 完全跑不到新数据上。
- 修复（2026-11-02）：重写为 **v2 结构校验器**，读 `games_*.jsonl` 的 `decision` / `game` 两种记录，检查：
  字段齐全、同局内 `seed`/`level`/`policy` 一致、名次是 `0..3` 的排列、`team_rank` 与实际名次一致、
  `selected_index` 在范围内、`pass`/`play` 与 `action` 自洽、四家手牌总数 ≤ 108、
  `hand` 长度与 `hand_counts` 一致。**不再**读 v1 的 `state` / `candidate_actions`。
- 实测（300 局文件）：`对局：300   决策：27794`、`结构校验通过。`
- **分工没变，也别搞混**：`check_dataset.py` 只证明「文件结构没坏」（秒级、不调引擎）；
  **完整语义校验**（重放整局 + 候选重算 + 标签对齐）仍由 `training/export_dataset.py` 负责。
  正式数据两个都要跑。

### 4.4 【限制】编码器 v2 的边界

`training/state_encoder.py` 已经是 v2（**状态 198 维、动作 65 维**），比 v1（59 / 26）严格更好：
保留花色、带已出牌池、带级牌与 `pass_count`、座位改相对位置、过牌用独立 flag。
但仍有限制：

| 限制 | 说明 |
|---|---|
| 只编码「观测者视角」 | 假定观测者就是当前行动者；不支持离线旁观视角（模块文档已注明） |
| 手牌计数归一化除以 2 | 两副牌同花色同点数最多 2 张，超出会被截断（数据异常时静默饱和） |
| 不含「进贡/升级」状态 | 这些规则还没实现 |
| 不含对手手牌 | 正确（防信息泄漏），但也意味着模型必须自己推断 |
| 不含历史动作序列 | 只有上一手 + 已出牌池 + `pass_count`，没有完整时序 |

### 4.5 【限制】候选动作不完整（连对/飞机只取一个花色解）

- `game_engine/legal_moves.py` 把牌型分成「枚举花色」和「只取规范解」两类：
  单张/对子/三张/炸弹/顺子/三带二 会枚举花色组合；
  **连对 / 连续飞机 只取一个规范组合**（`available[:count]`）。
- 后果：候选集合不是数学上的全集。例如手里有两张不同花的 5，`55 66` 只会生成其中一种花色搭配。
  不影响「这手牌能不能出」的判定，但会影响「保留哪张花色去凑同花顺」的选择空间。
- 实测规模：27 张手牌（seed=42、玩家 0、无级牌模式）一次生成 **301** 个候选；
  测试里的上界是 800（`tests/test_legal_moves.py::test_candidate_count_is_reasonable`）。
- ⚠️ 开级牌 + 手里有逢人配时，候选数会**暴涨**，见 4.11。

### 4.6 【已修复】Heuristic 不感知级牌

### 4.9 【工程】单进程、无并发

### 4.11 【仍是短板，但已被数据缓解】候选空间太大

- 实测：300 局 **平均候选 23.21 / 最大 1635**；2000 局 **23.09 / 1601**；3000 局 **23.24 / 2014**；
  合并 5000 局 **23.18 / 2014**。
  最大值来自「领出时手里含逢人配」——万能牌可替代任意牌，生成器会把大量序列候选都枚举出来。
- 内存问题已解决：`training/dataset.py::collate` 按**批内实际最大宽度**补边，
  并把候选数接近的样本排到一起（`make_batches` 先按长度排序再切批），
  所以 46 万样本 / 最大 2014 候选也能在单卡上训完（v7 40 轮约 10 分钟）。
  `export_dataset.py::pad_candidates(..., max_width=...)` 也支持显式指定宽度。
- **学习问题也已部分缓解**：加数据后最难的一桶（101+）从 0.234 涨到 **0.429**（见 4.12）。
  但仍是最弱环节；候选裁剪（RULES.md Q13）依然值得做，主要价值是**降低后续自我对弈的采样成本**。
- 待确认项（RULES.md Q3 第 10 条 / Q13）：生成器会产出
  「真实牌已齐、却仍用逢人配替换其中一张」的冗余序列候选，是否要在生成阶段裁掉，需要负责人拍板。

### 4.12 【短板】候选越多越难，但加数据能明显抬尾部

参考模型 **v7** 在验证集（27,725 条，已剔除无选择样本）上的分桶一致率，
与 2000 局模型（v2）对照：

| 候选数量 | 样本数 | v7 一致率 | v2 一致率 |
|---|---:|---:|---:|
| 2 | 5,383 | **0.990** | 0.910 |
| 3–5 | 5,949 | 0.815 | 0.747 |
| 6–20 | 8,530 | 0.697 | 0.553 |
| 21–100 | 5,263 | 0.560 | 0.356 |
| 101+ | 2,600 | **0.429** | 0.234 |

- 读法：只有 2 个候选（多数是「跟牌 / 过牌」二选一）时几乎全对；
  候选上百（几乎都是**领出**）时只有 43% 左右，仍是最弱的一环。
- **关键结论：每加一次数据，最难的那一桶涨得最多**（101+：0.234 → 0.429）。
  所以候选空间大是短板，但**不是只能靠裁候选解决**——数据和表示同样有效。
- 剩余可做的事情（按性价比）：候选裁剪（Q13，顺带降低自我对弈采样成本）> 更多数据 > 改状态表示。
- ❌ 不要指望「多训练几轮就能解决」：轮数只在数据足够时才有用，见 4.13。

### 4.13 【教训（已修正）】轮数与数据量是耦合的，不能单独说「轮数没用」

| 数据 | 轮数 | 验证 loss | 验证一致率 | 对启发式（400 局） |
|---|---|---|---|---|
| 2000 局 | 20 | **1.82** | 0.594 | 25.75% |
| 2000 局 | 40 | 2.09 | 0.581 | 23.33%（**过拟合**） |
| 5000 局 | 20 | — | 0.684 | 39.75% |
| 5000 局 | 40 | 1.10 | **0.728** | **51.50%**（**有效**） |

- 同样「20 → 40 轮」：2000 局时**变差**（过拟合），5000 局时**大涨**（25.75% → 51.50% 是数据量 2000→5000 的功劳，
  5000 局内部 20→40 轮是 39.75% → 51.50%）。
- 结论：**轮数能不能加取决于数据量**。本文件早期版本写的「训练轮数不是瓶颈」是**错的，已更正**。
  正确说法是「在 2000 局这个数据量下，加轮数没用；到 5000 局就有用了」。

### 4.14 【方法论】整体一致率会被「无选择样本」抬高

- 只有 1 个候选的样本占比：300 局 **39.3%**、2000 局 **40.2%**、合并 5000 局 **40.1%**。
  它们恒为 100%，没有学习信号，却会在损失里占掉四成权重。
- 现在训练与评估默认 `--min-candidates 2` 剔除：
  2000 局按局切分后训练集 166,055 → **99,194 条**，验证集剩 **11,225 条**；
  合并 5000 局保留 ≥2 候选的样本 **275,471 条**，v7 的验证集 **27,725 条**。
- ⚠️ **报一致率必须说明有没有剔除**。v1 的 0.714 就是被这类样本抬高的，不能和后面几版比。

### 4.15 【口径】神经网络评估的三个坑

1. **`--level` 必须给具体级牌**（如 `--level 2`）。数据集是 level 轮转采的，
   `level=None`（无级牌模式）属于**训练分布外**输入，拿它评估没有意义。
2. **确定性策略 vs 随机策略**：NeuralPolicy 是 argmax（无随机性）；
   启发式带随机数、且成对评估里两边座位各自有种子。两者「随机性条件」不同，
   比较胜率时要在文档里写清，不许只丢一个百分数。
3. **默认 checkpoint 是最新而非最好**：`players.neural.register()` 与 `evaluate_neural`
   不带 `--checkpoint` 时按修改时间取最新，目录里既有 v7 也有 v3/v4/v5 这些**故意做差的对照模型**。
   正式评估必须显式指定 `models\bc_v7_5000_40ep.pt`。

### 4.16 【负结果】把「花色排列」当等价答案会掉点，花色不是噪声

- 动机：领出时候选常达上千个，很多只是同一手牌换了花色、老师在其中随机挑，
  看起来像标签噪声。于是试了置换等价损失 `-log Σp`（`--loss group`）与混合 `ce + λ·group`（`--loss mixed`）。
- 结果（全部 400 局配对 / 或 120~200 局评估）：

  | 方案 | 对启发式 | 说明 |
  |---|---|---|
  | 纯交叉熵（ce） | 25.75% | 基线 |
  | 纯等价损失（group） | **19.25%** | 配对 400 局，McNemar 精确双尾 **p = 0.027**，显著更差 |
  | mixed λ=0.1 | 18.00% | 更差 |
  | mixed λ=0.3 | 25.75% | 与基线持平 |
  | mixed λ=0.5 | 25.25% | 略差 |

- 原因：**花色不是噪声**——留哪张花色会影响后续的逢人配与同花顺，合并掉等于丢真实信息。
- 处置：实现保留在 `--loss group|mixed` 下作为对照，**默认仍是 `ce`**。
  这条负结果已写进 `models/README.md`，不许从文档里删掉。
